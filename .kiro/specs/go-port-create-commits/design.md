# Go Port of create_commits.py Design

## Overview

This feature ports the Python CLI tool `create_commits.py` to Go with full behavioral parity, under a new Go module published at the vanity import path `go.nwlabs.dev/push-signed-commits`. The tool reads commits from a local branch that are not yet on a corresponding remote branch and recreates each of those commits on the remote branch through GitHub's GraphQL `createCommitOnBranch` mutation. Because that mutation performs commit signing and authorship attribution on GitHub's side, the recreated commits are verified commits whose hashes differ from the local commits.

The Go port matches the Python tool's observable behavior for the command-line interface, git interactions, payload chunking, GraphQL request construction, error handling, and logging. The single intentional deviation is the rebase-first step described in Requirement 5: before verifying divergence, the Go port fetches the latest upstream and attempts a rebase of the local branch onto `<remote_name>/<remote_branch_name>`. When the rebase cannot complete cleanly, the tool aborts the rebase and exits without auto-resolving anything. The Python implementation performs no rebase.

The command is implemented as a single-purpose root command built on Cobra, wrapped with Fang for execution, configured through koanf, and logged through `go.nwlabs.dev/x/logutils`. Git access prefers the `go-git` library and falls back to `os/exec` only where `go-git` lacks the required capability. GraphQL access uses type-safe client code generated by `github.com/Khan/genqlient` from GitHub's committed GraphQL schema. Tests are traditional table-driven Go tests using the standard `testing` package; property-based testing is explicitly not used.

### Research notes

The following findings informed the design.

* **GraphQL client approach.** The Python tool issues a single POST to `https://api.github.com/graphql` with a `Bearer` token and interprets the raw JSON response (`data`, `errors`, `errors[].type == "STALE_DATA"`, `data.createCommitOnBranch.commit.oid`). The Go port uses `github.com/Khan/genqlient` to generate type-safe client code from GitHub's GraphQL schema, which gives compile-time validation of the `createCommitOnBranch` operation and its input types and removes the hand-written request/response structs. The `STALE_DATA` distinction is preserved because genqlient surfaces GraphQL-level errors as a `gqlerror.List` (from `github.com/vektah/gqlparser/v2/gqlerror`); each `*gqlerror.Error` carries `Message`, `Path`, and an `Extensions map[string]interface{}`, and GitHub reports the stale-head condition through the error's `type`, which appears as `Extensions["type"] == "STALE_DATA"` (with message inspection as a fallback). See the [genqlient documentation](https://github.com/Khan/genqlient).

* **go-git coverage.** `go-git` (`github.com/go-git/go-git/v5`) provides object and tree access (`CommitObject`, `Tree`, `TreeEntryFile`, blob readers), `Log`, `MergeBase`, `Fetch`, `ResolveRevision`/`rev-parse`, and remote listing (`ListContext`, equivalent to `git ls-remote`). It does **not** provide a rebase operation, and its `--name-status` equivalent does not expose git's rename detection (`R<score>`) status codes in the form the Python tool parses. Those two operations fall back to `os/exec`. See the [go-git documentation](https://pkg.go.dev/github.com/go-git/go-git/v5).

* **Rename detection.** The Python tool depends on `git diff --name-status` emitting `R100 old new` style lines so it can model a rename as a deletion of the old path plus an addition of the new path. Reproducing git's rename scoring in pure `go-git` is not practical, so the file-change derivation shells out to `git diff --name-status <hash>^ <hash>` and parses the tab-separated output exactly as the Python tool does.

* **Binary-safe content.** The Python tool reads file content with `git show <hash>:<file>` in binary mode and base64-encodes the raw bytes. `go-git` can read the same bytes through the commit tree's blob reader, which avoids a subprocess. The design uses `go-git` for this read while keeping the base64 behavior identical.

## Architecture

The tool runs as a linear pipeline. Argument parsing and branch validation happen first and never touch the network. Remote verification (existence, fetch, rebase, merge-base, divergence) happens next. Only after verification succeeds does the tool collect commits, build per-commit payloads, chunk them, and push them in order while chaining the expected head OID.

```text
                         +------------------------+
   CLI flags  ---------> |   cmd (root command)   |
   env / config -------> |   koanf resolution     |
                         +-----------+------------+
                                     |
                                     v
                         +------------------------+
                         |   Branch_Validator      |  (no network / no git)
                         +-----------+------------+
                                     |
                                     v
                         +------------------------+       +---------------------+
                         |   Git_Client            |<----->|  go-git repository  |
                         |  ls-remote / fetch      |       +---------------------+
                         |  rebase (os/exec)       |<----->|  git subprocess     |
                         |  merge-base / rev-parse |       +---------------------+
                         |  rev-list / log / show  |
                         |  diff --name-status     |
                         +-----------+------------+
                                     |
          +--------------------------+---------------------------+
          |                          |                           |
          v                          v                           v
 +------------------+     +----------------------+     +---------------------+
 | Commit_Collector |     |  File_Change_Builder |     |      Chunker        |
 |  rev-list order  |     |  A / M / R / D model |     |  split at threshold |
 +--------+---------+     +----------+-----------+     +----------+----------+
          |                          |                           |
          +--------------------------+---------------------------+
                                     |
                                     v
                         +------------------------+       +---------------------+
                         |     Commit_Pusher       |----->|   GraphQL_Client    |
                         |  expectedHeadOid chain  |<-----|  createCommitOnBranch|

                         +------------------------+       +---------------------+
```

## Components and Interfaces

All interfaces are named and declared at package level so that git access and GraphQL access can be replaced with fakes in table-driven tests. No anonymous interfaces are used.

### GitClient

`GitClient` abstracts every git operation. The production implementation wraps a `go-git` repository and falls back to `os/exec` for rebase and name-status derivation. Test code substitutes a fake that returns table-defined outputs.

```go
// GitClient performs the local git operations the tool needs. Methods return
// wrapped errors; none call os.Exit.
type GitClient interface {
    // RemoteBranchExists reports whether the remote branch exists, mirroring
    // `git ls-remote --exit-code --heads <remote> <branch>`. A missing branch is
    // reported as (false, nil); only unexpected failures return a non-nil error.
    RemoteBranchExists(ctx context.Context, remoteName, remoteBranchName string) (bool, error)

    // FetchRemoteBranch runs the equivalent of `git fetch <remote> <branch>`.
    FetchRemoteBranch(ctx context.Context, remoteName, remoteBranchName string) error

    // RebaseOnto attempts `git rebase <remote>/<branch> <local>` and, on failure,
    // runs `git rebase --abort` before returning an error.
    RebaseOnto(ctx context.Context, opts *RebaseOptions) error

    // MergeBase returns the OID from `git merge-base <local> <remote>/<branch>`.
    MergeBase(ctx context.Context, opts *MergeBaseOptions) (string, error)

    // RemoteHeadOID returns the OID from `git rev-parse <remote>/<branch>`.
    RemoteHeadOID(ctx context.Context, remoteName, remoteBranchName string) (string, error)

    // CommitsNotOnRemote returns oldest-to-newest local commit hashes from
    // `git rev-list <remote>/<branch>..<local>`.
    CommitsNotOnRemote(ctx context.Context, opts *CommitRangeOptions) ([]string, error)

    // CommitMessageBody returns the full message from `git log --format=%B -n 1 <hash>`.
    CommitMessageBody(ctx context.Context, commitHash string) (string, error)

    // NameStatus returns the raw lines of `git diff --name-status <hash>^ <hash>`.
    NameStatus(ctx context.Context, commitHash string) ([]string, error)

    // FileContentsAtCommit returns the raw bytes of a file at a commit, mirroring
    // `git show <hash>:<path>` in binary mode.
    FileContentsAtCommit(ctx context.Context, commitHash, path string) ([]byte, error)
}
```

### GraphQLClient

`GraphQLClient` sends the `createCommitOnBranch` mutation and interprets the response. The production implementation wraps the genqlient-generated `createCommitOnBranch` function and maps genqlient errors to the package sentinels; tests substitute a hand-written fake that returns table-defined OIDs or sentinel errors. The interface is retained as the seam for table tests even though the underlying call is generated.

```go
// GraphQLClient creates commits through GitHub's GraphQL API.

    // created commit OID, or a wrapped sentinel error describing the failure.

}
```

## Data Models

The GraphQL input and response types are generated by genqlient from `schema.graphql`, so they are not hand-written. genqlient emits the GitHub input objects `CreateCommitOnBranchInput`, `CommitMessage`, `FileChanges`, `FileAddition`, `FileDeletion`, and `CommittableBranch` (the branch selector, carrying `repositoryNameWithOwner` and `branchName`), plus the request and response types for the `createCommitOnBranch` operation and its `commit { oid }` selection. These generated types serialize to the exact GraphQL field names, so the payload stays byte-compatible with the Python request and the chunker's size estimate matches the real payload. The former hand-written `graphQLRequest`, `graphQLResponse`, `responseData`, and `responseError` structs are removed; genqlient owns request and response decoding.

The Chunker and File_Change_Builder operate on the generated `FileChanges`, `FileAddition`, and `FileDeletion` types for both building the change set and estimating payload size (`json.Marshal` of the generated types), so a single set of types is used end-to-end and the serialized bytes remain identical.

The production code defines one small hand-written input struct that carries the per-call values into the thin wrapper, which maps them onto the generated input types before invoking the generated function. The token is carried out of band (it is applied by the HTTP transport, not serialized into the mutation variables).

```go
// CreateCommitInput carries the per-call values into the GraphQLClient wrapper,
// which maps them onto the genqlient-generated input types. The token is applied
// by the HTTP transport and is never serialized into the mutation variables.
type CreateCommitInput struct {
    RepositoryNameWithOwner string            // used for messages and the branch selector
    RemoteBranchName        string            // used for messages and the branch selector
    ExpectedHeadOid         string            // mapped to CreateCommitOnBranchInput.expectedHeadOid
    FileChanges             githubgql.FileChanges // genqlient-generated type
    Message                 githubgql.CommitMessage // genqlient-generated type
}
```

The configuration model holds resolved flag values and is populated by koanf.

```go
// Config holds the resolved input values for one run.
type Config struct {

```

## Command-line interface and configuration

The root command registers the five required named flags plus the optional verbosity counter in `init()` (marked `// lint:allow_init`). Flag variables use the lowercase `f` prefix.

| Flag                           | Variable         | Required | Default | Consumer                          |
|--------------------------------|------------------|----------|---------|-----------------------------------|
| `--github-token`               | `fGithubToken`   | yes      | none    | GraphQL_Client transport (Bearer) |
| `--repository-name-with-owner` | `fRepoWithOwner` | yes      | none    | GraphQL mutation branch object    |
| `--local-branch-name`          | `fLocalBranch`   | yes      | none    | Branch_Validator, Git_Client      |
| `--remote-name`                | `fRemoteName`    | yes      | none    | Branch_Validator, Git_Client      |
| `--remote-branch-name`         | `fRemoteBranch`  | yes      | none    | Branch_Validator, Git_Client      |
| `--verbose` / `-v`             | `fVerbose`       | no       | `0`     | logutils configuration            |

Configuration resolves through koanf in the repository's standard priority order: CLI flag, then environment variable, then local config, then user config (`$XDG_CONFIG_HOME/push-signed-commits`), then global config (`/etc/push-signed-commits`). Required flags are enforced by Cobra's required-flag mechanism, which reports a usage error and exits non-zero when any is omitted. Flag values are passed to consumers without transformation, satisfying the parity requirement that string values are not altered.

`Execute()` builds a `context.Background()`, passes it through `fang.Execute()`, and `os.Exit(1)` runs in `main`/the Execute wrapper on error. `RunE` wires the pipeline: validate branch names, construct the `GitClient` and `GraphQLClient`, run remote verification, collect commits, build and chunk payloads, and push. Every non-top-level failure returns a wrapped error.

## Logging

Logging uses `go.nwlabs.dev/x/logutils`, configured at startup from the `--verbose` / `-v` count (default `0`), so informational and debug messages are suppressed by default. The count maps to a level: `0` is `WARN`, `-v` (`1`) is `INFO`, and `-vv` or more (`>= 2`) is `DEBUG`, clamped at `DEBUG`. All structured logging uses the slog `*Context` variants (`DebugContext`, `InfoContext`, `WarnContext`, `ErrorContext`) with the request context. Log keys are `snake_case` constants defined in `cmd/logkeys.go`; messages are capitalized. The events logged mirror the Python implementation at each level.

| DEBUG | List of commit hashes to be created                                                  | Commit_Collector    |

## GraphQL client design

`CreateCommitOnBranch` reproduces the Python `create_commit_on_remote_branch` behavior while delegating the wire work to the genqlient-generated function.

Code generation is driven by a `//go:generate go run github.com/Khan/genqlient` directive in `generated.go` and configured by `genqlient.yaml`. The configuration points at the committed `schema.graphql` and the `operations.graphql` operation file and writes the generated types and function into the `githubgql` package.

```yaml
schema: schema.graphql
operations:
  - operations.graphql
generated: generated.go
package: githubgql
```

GitHub's GraphQL schema is large, so `schema.graphql` is fetched (or vendored) from GitHub's public GraphQL schema and committed to the repository; a trimmed schema covering `createCommitOnBranch` and its input and payload types is sufficient, and the full schema may be committed instead. Committing the schema makes generation reproducible and gives compile-time validation of the operation against the real types.

The operation is declared once in `operations.graphql` and validated against the committed schema at generation time.

```graphql
mutation createCommitOnBranch($input: CreateCommitOnBranchInput!) {
  createCommitOnBranch(input: $input) {
    commit {
      oid
    }
  }
}
```

* **Client construction.** The wrapper builds `graphql.NewClient("https://api.github.com/graphql", httpClient)`, where `httpClient` is an `*http.Client` whose `Transport` is a custom `http.RoundTripper` that sets `Authorization: Bearer <github_token>` on every request. The token is applied by the transport, so it never appears in the mutation variables.
* **Timeout.** The 600-second timeout is applied through the `http.Client` `Timeout` (or an equivalent per-request `context.Context` deadline).

* **Invocation.** The wrapper maps `CreateCommitInput` onto the generated `CreateCommitOnBranchInput` (branch selector with `repositoryNameWithOwner` and `branchName`, `expectedHeadOid`, `fileChanges`, and `message`), calls the generated `createCommitOnBranch` function, and then interprets the returned `(resp, err)` pair.

* **Response interpretation**, preserving the Python tool's ordering and the Requirement 11 semantics:

  1. If `err` is non-nil but does not convert to a `gqlerror.List` via `errors.As` (a transport or HTTP-level failure, including a `graphql.HTTPError` for a non-200 response), raise `Github_API_Error` stating the response had an unexpected format and include the response content. (Requirement 11.4, 11.7)

  2. If `err` converts to a `gqlerror.List` and any entry indicates `STALE_DATA` (`Extensions["type"] == "STALE_DATA"`, falling back to message inspection), raise `Partial_Push_Failure` stating the expected head OID is stale and the operation is aborting. (Requirement 11.5)

  3. If `err` converts to a `gqlerror.List` with no `STALE_DATA` entry, raise `Github_API_Error` including the error messages. (Requirement 11.6)

  4. If `err` is nil but the created commit OID is absent (`resp.CreateCommitOnBranch.Commit` is nil or its `Oid` is empty), raise `Github_API_Error` stating the response had an unexpected format and include the response content. (Requirement 11.7)

  5. Otherwise return the OID and log the created commit OID and branch. (Requirement 11.8)

The ordering preserves the Python control flow: genqlient's own decoding handles the old "missing `data` field" case (Requirement 11.4), which now manifests as either a transport-level error with no usable `gqlerror.List` or a nil/empty commit result, both mapped to the `Github_API_Error` "unexpected format" branch. A `gqlerror.List` with no `STALE_DATA` entry remains a distinct non-stale GraphQL error, so the `STALE_DATA` distinction is never hidden behind a generated error type.

## Chunking algorithm

The Chunker reproduces the Python `chunk_file_changes` logic. Payload size is estimated as the byte length of the UTF-8 JSON serialization of the `FileChanges` object (via `json.Marshal`), which matches the real request body because the JSON field names are identical.

```text
estimate(fc) = len(json.Marshal(fc))

if estimate(whole) <= MAX_PAYLOAD_BYTES:
    return [whole]                      # single chunk equal to the original

warn("~<MB> MB exceeds threshold; splitting")

current = FileChanges{additions: [], deletions: whole.deletions}   # deletions in first chunk
currentSize = estimate(current)
chunks = []

for addition in whole.additions:
    addSize = len(json.Marshal(addition))
    if currentSize + addSize > MAX_PAYLOAD_BYTES and len(current.additions) > 0:
        chunks.append(current)
        current = FileChanges{additions: [], deletions: []}
        currentSize = estimate(current)
    current.additions.append(addition)
    currentSize += addSize

if len(current.additions) > 0 or len(current.deletions) > 0:
    chunks.append(current)

info("split into <n> chunks")
return chunks
```

Key behaviors preserved from the Python tool: all deletions go into the first chunk; a new chunk is started only when adding the next addition would exceed the threshold and the current chunk already holds at least one addition (so a single oversized addition is never dropped and never forces an empty chunk); and the final chunk is appended only when it holds at least one addition or deletion. The threshold is the named constant `MaxPayloadBytes = 40 * 1024 * 1024`.

## Push orchestration and expectedHeadOid chaining

`Commit_Pusher` reproduces the Python `main` push loop.

* The first commit (first chunk of the first local commit) uses the `Merge_Base_OID` as `expectedHeadOid`.

* Every subsequent chunk uses the OID of the most recently created commit as `expectedHeadOid`.

* Before creating the next commit, when at least one commit has already been pushed, the pusher re-fetches the remote head OID (`FetchRemoteBranch` then `RemoteHeadOID`) and compares it to the most recently created OID. A mismatch raises `Partial_Push_Failure` reporting the count and hashes of commits already pushed and the local commits not pushed (`localHashes[len(created):]`), and exits non-zero.

* For a commit split across multiple chunks, each chunk's headline is annotated with ` (part <index+1>/<count>)` while the body is unchanged. A single-chunk commit uses the unmodified `CommitMessage`.

* Each created OID is recorded as the most recently created commit and appended to the created-hashes list.

* After all commits are created, the pusher logs the total number created on the remote branch.

The commit-message construction (Requirement 7) builds the headline from the first line of `git log --format=%B -n 1 <hash>` (trimmed), the body from the remaining lines joined by `\n`, and then appends `\n\n` followed by `This commit was created from the local commit with hash <commit_hash>.`.

File-change derivation (Requirement 8) parses each `git diff --name-status <hash>^ <hash>` line on tab characters into a status field and one or more filename fields:

* `A` or `M`: add a `FileAddition` whose path is the last filename field and whose contents are the base64-encoded bytes of that file at the commit.
* status containing `R` (including scored forms like `R100`): add a `FileDeletion` for the first filename (old name) and a `FileAddition` for the second filename (new name) with its base64-encoded contents at the commit.
* `D`: add a `FileDeletion` whose path is the first filename field.

File contents are read as raw bytes (Requirement 9) and base64-encoded into a UTF-8 string for the `FileAddition`.

## Git operation mapping

The table records which operations use `go-git` and which must shell out through `os/exec`, with the reason for each fallback.

| Operation                  | Python command                                        | Go implementation                                               |
|----------------------------|-------------------------------------------------------|-----------------------------------------------------------------|
| Remote branch existence    | `git ls-remote --exit-code --heads <remote> <branch>` | go-git `Remote.ListContext` filtered to the branch ref          |
| Fetch remote branch        | `git fetch <remote> <branch>`                         | go-git `Repository.FetchContext`                                |
| Rebase onto upstream       | (new in Go port, Requirement 5)                       | os/exec `git rebase` (no go-git rebase support)                 |
| Abort rebase               | (new in Go port, Requirement 5)                       | os/exec `git rebase --abort`                                    |
| Merge base                 | `git merge-base <local> <remote>/<branch>`            | go-git `Repository.MergeBase`                                   |
| Remote head OID            | `git rev-parse <remote>/<branch>`                     | go-git `Repository.ResolveRevision`                             |
| Commits not on remote      | `git rev-list <remote>/<branch>..<local>`             | go-git `Repository.Log` walking the range (reversed)            |
| Commit message body        | `git log --format=%B -n 1 <hash>`                     | go-git `CommitObject.Message`                                   |
| File changes (name-status) | `git diff --name-status <hash>^ <hash>`               | os/exec `git diff --name-status` (rename scoring not in go-git) |
| File contents at commit    | `git show <hash>:<file>`                              | go-git commit tree blob reader                                  |

The two `os/exec` fallbacks are the rebase step (go-git has no rebase) and the name-status diff (go-git does not surface git's rename-detection status codes in the `R<score>` form the parser relies on). Both construct their argument vectors from discrete, validated inputs rather than a shell string, and paths are composed with `filepath.Join` where applicable for Windows safety.

## Error Handling

Sentinel errors live in `cmd/errors.go` in a single `var()` block. Names use the `Err` prefix and PascalCase, each with its own doc comment. Dynamic detail is added at the call site with `fmt.Errorf("%w: %s", ErrSentinel, detail)`.

| Sentinel                  | Python exception            | Raised when                                                                                  | Requirement      |
|---------------------------|-----------------------------|----------------------------------------------------------------------------------------------|------------------|
| `ErrRemoteBranchNotFound` | `RemoteBranchNotFoundError` | Remote branch existence check reports the branch does not exist.                             | 4.2              |
| `ErrRebaseAborted`        | (new)                       | Rebase reports conflicts or cannot complete cleanly; the rebase is aborted, no auto-resolve. | 5.3              |
| `ErrRemoteBranchDiverged` | `RemoteBranchDivergedError` | Remote head OID is not equal to the merge base before pushing begins.                        | 5.6              |
| `ErrGithubAPI`            | `GithubAPIError`            | Transport/HTTP error, non-STALE_DATA `gqlerror.List`, or nil/empty created commit OID.       | 11.4, 11.6, 11.7 |
| `ErrPartialPushFailure`   | `PartialPushFailure`        | `STALE_DATA` error from GraphQL, or re-verified remote head does not match the last push.    | 11.5, 12.4       |

Behavior around the push loop (Requirement 13):

* A `Remote_Branch_Diverged_Error` or `Github_API_Error` while creating a commit when no commit has yet been pushed logs an error stating the failure occurred on the first commit and that no changes were made to the remote branch, then propagates the error.

* The same error classes after at least one commit has been pushed propagate without claiming the remote branch is unchanged.

* Every unrecoverable error defined in this specification propagates to the top level, where the command exits with a non-zero exit code. `os.Exit` is confined to `main`/the Execute wrapper; all other functions return wrapped errors.

Git command failure handling (Requirement 14): any git operation the Python tool runs with `check=True` is treated as an error when it fails, causing a non-zero exit. The remote branch existence check is the sole exception; its exit code is interpreted (branch present or absent) rather than treated as fatal, so a missing branch yields `(false, nil)` and the caller raises `ErrRemoteBranchNotFound`.

## Testing Strategy

The test suite uses traditional, table-driven Go tests built on the standard `testing` package with `github.com/go-openapi/testify` assertions. Property-based testing is explicitly **not** used for this feature, per Requirement 15. The `GitClient` and `GraphQLClient` interfaces are satisfied by hand-written fakes so each behavior is exercised against table-defined inputs without a live repository or network.

Behaviors covered by table-driven tests:

* **Branch name validation.** Local and remote names with `origin/`, `refs/heads/`, and `<remote_name>/` prefixes each produce the correct error and a non-zero result; clean names pass. (Requirements 2, 15.3)

* **File-change derivation.** `A`, `M`, `R` (including scored `R100`), and `D` name-status lines each map to the correct additions and deletions, including the rename case that produces both a deletion of the old path and an addition of the new path. Tab-splitting selects the last filename for additions and the first for the rename deletion. (Requirements 8, 9, 15.3)

* **Payload chunking.** A payload at or below the threshold returns a single chunk equal to the original; a payload above the threshold places deletions in the first chunk, starts a new chunk only when the next addition would exceed the threshold and the current chunk already has an addition, and never appends an empty final chunk. (Requirement 10, 15.3)

* **Commit message construction.** Single-line and multi-line messages produce the correct headline and body, and the body is suffixed with the two-newline provenance line naming the local commit hash. Multi-chunk headlines gain the ` (part i/n)` annotation while the body is unchanged; single-chunk commits are unmodified. (Requirements 7, 12.5, 12.6, 15.3)

* **GraphQL response interpretation.** A transport or HTTP-level error (not convertible to `gqlerror.List`) maps to `ErrGithubAPI`; a `gqlerror.List` with an entry whose `Extensions["type"]` is `STALE_DATA` maps to `ErrPartialPushFailure`; a `gqlerror.List` without a `STALE_DATA` entry maps to `ErrGithubAPI`; a nil-error response whose created commit OID is nil or empty maps to `ErrGithubAPI`; a well-formed success returns the OID. The genqlient-generated function is driven through a hand-written fake of `GraphQLClient` in standard table-driven tests (not property-based), and sentinels are matched with `errors.Is`. (Requirement 11, 15.3)

* **Push orchestration and chaining.** The first commit uses the merge base as `expectedHeadOid`; subsequent commits use the previous created OID; a re-verified remote head that no longer matches the last push produces `ErrPartialPushFailure` reporting pushed and unpushed hashes. (Requirement 12)

* **Rebase-abort path.** A rebase failure triggers `git rebase --abort` and yields `ErrRebaseAborted` without auto-resolving; a clean rebase proceeds to merge-base and divergence checks. (Requirement 5)

* **Error-handling branches.** A first-commit failure logs the no-changes message and propagates; a later failure propagates without the no-changes claim. (Requirement 13)

Integration-style coverage of the real `go-git` and `os/exec` paths (actual `git rebase`, `git diff --name-status`, blob reads) is exercised with a small number of representative fixture repositories rather than mocks, since those paths depend on real git behavior. These remain standard `testing` tests, not property-based tests.

## Deviations from the Python implementation

The Go port introduces one intentional behavioral deviation, defined in Requirement 5: a rebase-first step. After confirming the remote branch exists, and before verifying divergence, the Go port runs `git fetch <remote> <branch>`, then attempts `git rebase <remote>/<branch> <local>` so local commits are replayed on top of the latest upstream. If the rebase reports conflicts or cannot complete cleanly, the tool runs `git rebase --abort` to restore the pre-rebase state, raises `ErrRebaseAborted` instructing the operator to reconcile the branches manually, and exits non-zero without auto-resolving any conflict or rewriting already-pushed history. The Python implementation performs no rebase. Every other behavior retains full parity with the Python tool.
